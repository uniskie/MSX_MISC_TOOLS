# COMバイナリ to ROM(32KB page1-2) リロケータ逆アセンブラ

[Intev Tester](https://www.pastbytes.com/indevtester/index.html)をRAM8KBの機種でも動作させたくて作ったものです。

0100Hから始まるCOMファイルを4000Hから始まる16KB～32KBROMにリロケートするため、
命令、データ、ワークを識別し、アドレスにかかわる部分を解析してラベル化してASMファイルを出力する、
インテリジェント逆アセンブラっぽい物です。

遊びで作ったものです。

## 自己書き換えコードへの対応

- 自己書き換えコードをROM用に変換する処理は`Indev.com`で使用しているパターンにしか対応していません。
- 汎用性を狙うなら、RAMコピー実行モードというのもコマンドライン引数で有効にできます。  
  が、RAM16KBかつ、CODE部とWORKの合計が12KB以内という前提です。  
  固定データはROMを参照するため、ページ0と1はROMです。

## 環境

python 3.13用です。（特にmsx_symbols.pyの型指定など）

## 簡単な使用方法

1. `indev.com`を同じフォルダに配置

2. windowsであればstoreからpythonをインストールしておいて、コマンドラインから

   `> python com2rom.py⏎`

   で実行

   - 入力ファイル   ：`indev.com`
   - 出力ASMファイル：`indev_rom.asm`
   - 出力LOGファイル：`indev_rom.log`

3. 解析が終了するとROMようにリロケート変換した逆アセンブルリスト`indev_rom.asm`が生成されます。
   （※ 疑似的に全経路をトレース解析するので、時間がかかります）

4. [AILZ80ASM](https://github.com/AILight/AILZ80ASM/releases)を使用して`indev_rom.asm`をアセンブル。  
   ( `AILZ80ASM.exe`を同じフォルダに置いておいてください。 )  

## Intev Tester のターボR対応について

Indev TesterはターボRだとBIOSから削除されたタッチペンやアナログ入力周りが非対応です。

もちろん、本ツールでROM化しても同じです。

## VSCodeでこのフォルダをワークスペースとして開く場合

- `.vscode/launch.json` :  `F5`キーで`com2rom.py`をデバッグ実行

  各種引数セットがありますが、基本的に「引数 通常モード」で十分です。  
  他は実験用です。

- `.vscode/task.json` :  asmファイルを開いた状態で`shift+ctrl+b`でアセンブル実行

  [AILZ80ASM](https://github.com/AILight/AILZ80ASM/releases)を使用します。  
  `AILZ80ASM.exe`を同じフォルダに置いておいてください。  

## コマンドラインヘルプ

```
usage: com2rom.py [-i INPUT] [-o OUTPUT] [-a ADDRESS] [-s S] [-l L] [-c] [-n] [--patch] [--nopatch] [--asm-type {1,2}] [-h]

COMバイナリ to ROM(32KB page1-2) リロケータ逆アセンブラ v0.15.2

options:
  -i, --input INPUT     入力ファイルパス (16進数テキストまたはバイナリ)
  -o, --output OUTPUT   出力アセンブリファイルパス
  -a, --address ADDRESS
                        入力バイナリのMSX上での開始アドレスを指定 (16進数4桁、例: 0100)
  -s S                  RAMの先頭アドレスを指定 (16進数4桁、例: C000)
  -l L                  RAM使用上限アドレスを指定 (16進数4桁、例: EFFF)
  -c                    RAMコピーモード有効 (CODE+WORKをRAMへコピーして実行)
  -n                    通常モード有効 (CODEはROM上で実行、WORKのみRAMに配置)
  --patch               SMCパッチ有効 (通常モード時：JR命令書き換えをROM用処理でパッチ)
  --nopatch             SMCパッチ無効
  --asm-type {1,2}      アセンブラのタイプ (1 = sjasmplus, 2 = AILZ80ASM)
  -h, --help            コマンドライン引数のヘルプを表示
```

## トレース解析・再配置＆変換処理の概要

### トレース解析の目的

1. データ部分やワークエリアを識別
2. アドレスをラベル化することで、リロケータブルなASMファイルを得る
   - 分岐命令、アドレス間接参照命令は簡単
   - レジスタ指定のアドレス間接参照が問題

2は1が完了していないと判定できないので、
1と2で2つのパスに分けて実行解析を行います。

### トレース解析の課題

厳密なエミュレーションではなく、簡易的なシミュレーションであるため、スタックポインタや`JP (HL)`には対応していません。

これらには演算処理やメモリ操作への対応が必要ですが、現在対応していません。

- スタック操作を経由したRETによるジャンプは非対応
- JP (HL)は実行パス上での直近の`LD HL,nnnn`の値を使用

### パス1 : メモリ属性のスキャン

#### メモリ属性

メモリの用途によって

- CODE(プログラム)
- DATA（静的データ）
- WORK（書き込みあり）

の3種の属性を決定します。

属性分けが必要な理由としては主に

- 属性によってROMに配置するかRAMに配置するか決定
  - CODEやDATAはROMに配置
  - WORKはページ3のRAMに配置
  - RAMコピーモードではCODEもRAMに配置
- DATAは`DB`や`DW`で記述
- WORKに初期値があれば初期値をページ3RAMへ転送
- CODEへの書き込みがあれば自己書き換え(SMC) → ROMでは対策が必要
- ラベル化する際に用途に応じてラベル名を変えたい。

という理由があります。

1. 初期状態はDATA
2. 命令をデコードし、命令に応じた処理をしていく
   - PCを次の位置へ進め、実行スタックへ積む。
   - 命令を処理した範囲はCODE、書き込み命令の対象アドレスはWORKというように、
     RAMのアドレス毎に属性を付ける
3. CALLや条件分岐への対応
   - 分岐先を実行スタックへ積む
   - アドレス毎に処理済みフラグを書き込んで重複を防ぐ
4. 最終的にCODEでもWORKでもないところがDATA属性として残る

という形になります。

#### その他の検査

- WORKがアドレス値として利用されているかどうか
  - レジスタ間接参照命令があれば、そのレジスタへのロード処理を逆引きし、
    ロード処理がWORKからのロードであれば、そのWORKはアドレス格納用WORKである

  （これはパス2でのアドレス値ラベル化処理で必要な準備）

- WORKに続けて無参照のエリアがある場合、WORKへマージする  
  - Indev Testerでは文字列バッファの末尾文字が該当し、
    文字列バッファのWORKとマージして一緒にリロケートしないと文字表示周りが暴走する

- 【オプション】CODEとCODEに挟まれた未参照のエリアがあれば、未使用コードと判定する

各アドレスは1回だけスキャンすれば十分なので、比較的高速にスキャン終了しても基本的には問題ないと思われます。

### パス2 : 全実行経路の探索シミュレーション

値がアドレスかどうかを判断する時

- `LD (nnnn),A`や`JP nnnn`のように即値でアドレス指定する物
- `LD (HL),A`や`LDIR`のようにオペランドが即値でのアドレス指定になっていない物

に分かれます。

後者は値の用途を使用箇所からの逆引きで決定する必要があります。

- アドレスの指定方法

  - 即値指定
    - 即値でアドレスを指定した分岐命令  
      例） `CALL 0141H`
    - 即値での間接参照（アドレスとレジスタ間のロードストア）  
      例） `LD HL,(0005H)`
  
  - レジスタ指定
    - ロード・ストア、演算などの即値間接参照オペランド  
      例）`LD (HL),A`
    - ブロック転送命令
    - レジスタ指定に夜分岐命令  
      例） `JP (HL)`

- アドレスの種別
  - リロケート対象である元バイナリ範囲内へのアクセス
  - BIOSやシステムワークなどリロケート対象外へのアクセス

#### レジスタ指定で使用されるアドレス値の解決

レジスタでのアドレス指定があった場合、そのレジスタへ値をロードした位置を逆引きする必要あります。

1. 保存 （Register Stateの保存と管理）
   1. 各ペアレジスタに対して最後にレジスタロードが実行された位置と値を記憶しておく
   2. 間接参照ロードではワークエリアがアドレス値の格納に使用されているか把握しておく

2. 参照
   1. レジスタでのアドレス指定を行う命令があったら、
      直近のレジスタへの直近のロード処理をRegister Stateから逆引き
   2. アドレス格納用ワークエリアと判明したワークエリアへの書き込みを行ったら
      その値はアドレス値
      - 直近のレジスタへの直近の即値ロード処理をRegister Stateから逆引きし、
        その則値をアドレスラベルとして処理する

という手順になります。

（つまり、パス1の簡易探索でワークエリアがアドレス値格納用に使用されているかどうか検出しておく必要があります）

分岐や属性判定の為にはアドレス値に計算が挟まるケースも対応したいのですが、~~面倒くさい~~限界があるので、ある程度見切りをつけます。

具体的には以下のルール

- レジスタの値が破壊されるケースでは、ロード位置と値を破棄する

  - PUSH・POP
  - ビット操作、ローテートシフト、加減算

- 値は変更されるがロード位置の破棄はしない

  - 8bitレジスタのロード
    - 値は変更するが、16ビット値のロード位置は変更しない
  - 16bitレジスタのINC/DEC
    - 値は変更するが、16ビット値のロード位置は変更しない

- 情報の交換
  - 交換命令
  
### 自己書き換えコードの対策

- パッチ（コード置き換え）

  Indev Testerで使用している処理は固定なので代替処理に置き換える。

  ```
           LD   (JR_OP + 1), A
  .JR_OP:  JR .JP_TBL
  .JP_TBL: JP xxxx
           JP xxxx
           JP xxxx
           JP xxxx
           JP xxxx
           ...
  ```
  ↓
  ```
           ADD A, LOW .JP_TBL
           LD L, A
           LD A, HIGH .JP_TBL
           ADC A, 00H
           LD H, A
           JP (HL)
  .JP_TBL: JP xxxx
           JP xxxx
           JP xxxx
           JP xxxx
           JP xxxx
           ...
  ```

- RAMコピーモード

  メモリが C000H ～ EFFFHに収まるようであれば、
  CODE+WORKを丸ごとRAMにコピーにして実行する。

  パッチより汎用性があるが、メモリを多く消費する。
